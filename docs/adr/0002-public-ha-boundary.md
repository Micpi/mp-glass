# ADR 0002 — frontière HA et génération

Date : 2026-09-10. Statut : retenu.

Strategy `custom:mp-glass`, registration `window.customStrategies`, custom view et custom cards documentées. Les registries et services passent par la session HA du frontend. Aucun endpoint backend ne relaie une commande avec des droits administrateur. Module global chargé par helper frontend Python encapsulé : couplage HA à tester à chaque release. `async_register_static_paths` remplace l'ancien enregistrement synchrone.

Création du dashboard par le dialogue HA natif, sans modifier son stockage privé. La disponibilité du sélecteur communautaire et des suggestions fixe le minimum cible à 2026.6. Source : https://developers.home-assistant.io/docs/frontend/custom-ui/custom-strategy/

Le code HA stable 2026.9.1 fournit les helpers `frontend.add_extra_js_url` et `remove_extra_js_url`, explicitement destinés aux custom integrations. Ils sont encapsulés dans `custom_components/mp_glass/frontend.py` avec feature detection. Aucun accès direct au UrlManager interne n'est nécessaire. Si le helper disparaît, setup échoue explicitement ; le frontend standalone reste chargeable comme ressource Lovelace dans l'UI. Tester ce couplage sur chaque version HA supportée. Les composants privés du frontend ne sont jamais importés dans le JS. Source vérifiée : https://github.com/home-assistant/core/blob/2026.9.1/homeassistant/components/frontend/__init__.py

Complément 0.7.4 : HA sert les pages dès que `frontend` est prêt (`http` démarre sur `async_when_setup_or_start(hass, "frontend", …)`), avant les intégrations personnalisées, et n’insère les modules supplémentaires que dans les pages servies après leur ajout : le frontend 20260826 ne s’abonne pas à `frontend/subscribe_extra_js`. Le module est donc ajouté en tout premier dans `async_setup_entry`, avant toute tâche d’exécuteur, et conservé lors des rechargements de l’entrée ; seul `async_remove_entry` le retire. Le bootstrap déclare la stratégie sans aucun import. Le bundle principal, chargé ensuite sans limite de temps côté HA, est réessayé sous une autre adresse en cas d’échec, car un module dont le téléchargement a échoué reste en échec pour toute la page. La stratégie attend l’intégration tant que ses commandes répondent `unknown_command` ou `not_loaded`.

Complément 0.7.5 : la stratégie implémente `shouldRegenerate(config, oldHass, newHass)`, que le frontend consulte à chaque mise à jour d’état d’un dashboard stratégique affiché (`checkStrategyShouldRegenerate`, frontend 20260826). Tant qu’aucun dashboard n’a été demandé sur la page, elle répond une fois `true` : déclarée après l’abandon de HA, elle remplace l’erreur de délai. Ensuite, elle reprend la règle par défaut de HA (registres entités, appareils, pièces, étages). Le moteur remplace `generate` et `shouldRegenerate` ensemble, pour qu’ils suivent le même état. Le bootstrap est abaissé en ES2017 au build, pour qu’un navigateur trop ancien pour l’interface reçoive un message explicite plutôt que l’erreur de délai.
